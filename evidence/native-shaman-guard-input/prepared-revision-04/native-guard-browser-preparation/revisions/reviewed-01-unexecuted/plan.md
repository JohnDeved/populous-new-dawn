## Resource bounds

The original outer 300000-ms real-clock, shipped 1× bound remains authoritative,
including startup and all Save/Load work. There is no speed adjustment or simulated
turn. Entry/readiness must finish within 60000 ms of the harness receipt's start;
initial hut targeting must finish within 15000 ms. Training retains its 180000-ms
maximum and 30000-ms no-progress stop, but acquisition must leave at least 100000 ms
for the full guard, two checkpoint cycles and cleanup. Thus stage maxima are not
additive promises: late training is an incomplete resource-bounded attempt, not a
native timing defect. Do not extend a failed run's outer envelope.

Training and each pre/post-load observer are independent read-only RAFs, bounded by
elapsed time and at most 18000 rows (12000 undrained rows). Rows drain to JSONL at
roughly 500-ms host intervals and at action boundaries. After the initial full Blue
roster read, capture narrows to the actual Brave/Shaman plus all naturally appearing
Firewarriors; after conversion it narrows to the Firewarrior/Shaman. Every row
records its diagnostic actor scope. This avoids repeatedly exporting unrelated
followers while preserving the real allocation boundary. Native simulation remains
owned by the normal RAF/clock. Any omitted natural visits remain a limitation.

## Evidence and provenance

`witness.json`, `actions.jsonl`, `epoch-N-rows.jsonl`, screenshots and the maintained
harness receipt/server diagnostics form one attempt. The scenario adds all packet
file hashes plus Node/browser/Playwright/installed-lock/harness hashes before and
after because the maintained ephemeral path does not add profile runtime hashes.
The full source receipt binds clean tracked source and its actual head. Partial
logs survive failure. A capture cleanup error remains a failure; no fallback pass.

Observer native fields add guardInputPending, class/model, active queue/payload,
registered-object equality, alias/source identities, phase/counters/goals and
tribe shamanGuards/shamanGuardChanged. IDs are stable across all reads in one
browser document; explicit epoch numbers distinguish actual Load world replacements.
No identity number is compared across separate baseline/candidate browsers.

`provenance.json` identifies original source files, copied closure hashes and every
string adaptation. `runtime-sources.json` fingerprints the two allowed source
versions. `verify-preparation.mjs` checks those fingerprints, reconstructs exact
copied fragments, checks module syntax/importability, and runs narrow pure mocks for
integer hit rejection and clone ownership. Its result is source-only evidence.

## Review gaps and nonclaims

- This packet has not been independently reviewed or executed. It is not authorized
  to acquire a lane by its existence. Frozen input hashes, parent review and actual
  browser/dependency readiness are still required before either run.
- The new ground adapter, diagnostic data-module loading, fixed (25,-9)/(25,-1)
  target visibility/reachability, screenshot latency bounds and two-cycle orchestration
  require focused source review and actual browser confirmation. Authored terrain
  inspection motivates the points; it cannot establish accepted live movement.
- Training can finish between RAF samples; if occupancy/cost is not captured this
  attempt fails. CPU rendering or storage hashing can exceed the bound; retain that
  as an incomplete attempt, not a native defect or hardware result.
- Candidate assertions establish only this naturally trained single Firewarrior.
  Shared allocation across multiple followers, busy/mixed legacy whole-batch fallback,
  exhaustion, protected branches and replacement-Shaman cases retain their separate
  portable/native evidence. No actors are staged to broaden browser coverage.
- Independent RAF observations cannot prove every native visit, every phase setter,
  original-game visible pixels, complete animation lifecycle or hardware performance.
  A visible mesh/UV is not itself pixel evidence; review the actual retained images.
- Baseline/candidate screenshot comparison is valid only for corresponding source
  windows with the same packet hashes and viewport. No baseline image exists yet.

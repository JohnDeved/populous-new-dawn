# Delivery recovery

At resumption or a meaningful result, compare the issue's remaining acceptance with
the last PR update. Repeated unchanged checks, repeated triage, helper-only completion
claims, and recurring cleanup are signals to inspect the approach. Necessary native
research is useful when it resolves a named uncertainty with a concrete next result.

Use existing issue/PR history, diffs, source-bound receipts, and observed durations.
Do not maintain a second status ledger or periodically start delivery timers. Missing
historical timing stays unknown; parity coverage alone does not measure useful work.

The parent may use a read-only scout with one bounded brief: outcome, observed delay,
exact evidence, and the decision needed. Return at most three actionable findings,
the smallest correction, its cost/risk, and what next result would show improvement.
Do not create a contract or recursive process review for this diagnosis.

Apply the smallest supported correction: reuse valid evidence, narrow research,
fix a prerequisite, simplify coordination, or change the implementation approach.
Keep one feature owner through repair and PR review. If a concrete dependency blocks
that outcome, update its GitHub issue and continue other authorized useful work.

Preserve gameplay acceptance, modern performance, readable code, required native and
rendered proof, and review. Do not weaken tests, shrink scope, or count infrastructure
as gameplay to improve apparent progress. Record the cause/correction in the existing
issue or PR only when it changes routing or expectations, then resume delivery.

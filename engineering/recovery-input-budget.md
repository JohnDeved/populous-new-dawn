# Recovery introduction input budget

This is an explicit functional-contract migration, not a claim of faster input or a performance pass.

## Provenance

Commit `38072269e` introduced 2500 ms as a timeout on the retired public Skip button click. It did not measure a response-time SLA. Later `a74aa78e` bounded native state observation, Space delivery and verification together, and `985f2cfe` added real campaign-popup preparation inside that same allowance. Those stricter historical failures remain failures, not retroactively accepted results.

Hosted candidate `dbb9cd8c`, run `39678644125`, observed a valid public summary click taking 1754 ms: selector resolution, visibility/stability, scroll, trusted click and navigation completion all consumed time, without a logged obstruction or retry. The profile's full preparation exhausted 2500 ms at final owner observation. The pause job finished preparation in 1449 ms but expired during observed Space delivery. The trace does not isolate main-thread work from scheduling/transport costs.

## Opt-in setup callers

The profile's direct Load/new-mission entry, hosted pause recovery's mission entry, and the two hosted Tornado initial/restart readiness callbacks opt in when their runner supplies its existing absolute browser deadline. Other callers, including Mission10 and profile late-introduction readiness callbacks, keep the shared 2500 ms default unchanged. Local invocations without an outer deadline retain that default too.

Each opted-in action has one absolute deadline: the smaller of the existing public UI allowance and the remaining outer browser time. The profile allowance is 15000 ms (`freshPage` already uses that timeout). Pause uses at most the primary page's existing 25000 ms allowance, including its separate high-DPI contexts whose existing timeout is larger. This is not an additional allowance of setup time plus 2500 ms.

Tornado uses its existing 8000 ms page-action allowance, clipped by the current 12000 ms readiness wait's remainder, the same absolute at-most-90000 ms Tornado episode deadline, and the unchanged 180000 ms profile host deadline. Its callback still acts at most once per readiness wait, only for a positively observed interruptible flyby. Local episode expiry and outer abort reach the input cancellation signal. Each episode records initial/restart input phase timings. No readiness, episode, gameplay or host cap is increased.

At `bf15aab1` (Tutorial run `39684859007`), all nine profile cases passed and the three opted-in entry responses took approximately 638–795 ms after 2719–3419 ms of preparation. The job then failed in Tornado's first land readiness callback: the old shared 2500 ms bound expired while focusing after a real late popup closure, before Space. This is distinct from primary profile acceptance, and it is not a Tornado pass or a performance improvement.

The remaining shared-input callers were audited at that head. Profile's two late-readiness paths retain their 30000 ms readiness wait and 15000 ms page-action defaults inside the same 180000 ms host; neither callback acted in that run. Mission10's fresh entry retains its 15000 ms page-action default and shared 180000 ms host, including the Spy companion. At that head, the separate native-UI evidence adapter also retained its default and was not part of these eight hosted jobs. None is implicitly migrated by the optional callback arguments.

Initial preparation still observes owners, clicks each actual public summary, waits for its body to hide, verifies retained serial/open state, focuses the real world viewport and reobserves late owners. After this completes, a response deadline starts **before** fresh native-state observation, passive Space witness installation, trusted Space delivery and final verification. It is at most 2500 ms and is clipped to the already-running absolute action deadline. A positively witnessed popup rejection can repeat preparation only inside this same response deadline; it never resets either deadline.

Outer abort/deadline, setup expiry, response expiry, stale/native-completion races and original delivery errors remain observable failures. No pending operation may dispatch late Space after cancellation/expiry. Natural completion still sends no extra key, and accepted native input must preserve pause state. All original overall scenario/browser caps, gameplay turns, queues, stock and rendering assertions remain unchanged. Phase timestamps identify where the bounded action spent time. A response exceeding 2500 ms is still a failure.

At `7e33f7d9`, Tutorial run `39694511098` passed six of eight jobs. The profile's ninth usable-session case failed after a positively admitted popup-rejection retry: setup took about 569 ms, the first dispatch and final state read finished at 1279 ms, and retry preparation reached world focus just as the same response deadline expired at 3069 ms. That response failure remains a failure; the Tornado companion was not reached. The retained receipt did not include the passive event records, so its retry ownership could only be inferred from the exact source predicate, not independently inspected as raw event evidence.

Only already-opted-in recovery calls now combine passive witness finalization and fresh native after-state observation in one browser task after trusted Space resolves. The original listener cleanup happens first. A unique witness identity, a present live witness, actual record array and typed native state are required; missing or stale atomic evidence fails without a later-read fallback. Default callers retain their original array return and separate native-state read. Actual key-delivery errors still use the original fresh-state/error reconciliation, preserving natural completion and the original error.

Every attempted dispatch retains its fresh before-state, passive ownership records, atomic after-state when applicable, selected after-state source and outcome in the existing input trace. This is read-only diagnostic evidence, not permission to retry: the original trusted, nonrepeated, prevented, popup-owned, same-world and unchanged-state predicate still controls admission. No action, response or episode deadline is reset or increased. The effect on hosted elapsed time is unmeasured until a fresh rendered run.

Options and HUD ordinary Mission 1 entry now explicitly request the existing browser owner's 25000 ms page-action allowance, clipped to the one absolute episode deadline. The adapter passes that deadline and its existing cancellation signal from the original episode start, including initial context creation and navigation; each fallback context uses the same deadline rather than starting a new episode budget. The candidate pause-style supplement separately opts into its existing 25000 ms page-action allowance when that outer deadline is supplied. Deadline-less local pause invocations retain the shared default.

The candidate exports its supported `public-setup-then-response-v1` contract. Infrastructure rejects older helpers before mission UI entry and requires the helper's actual returned trace to identify the same contract, a bounded action and a response no longer than 2500 ms. Options, HUD and pause retain per-entry traces on failure as well as success; the adapter attaches its live receipt before calling an episode. No old failure is reclassified and no ambiguous input is retried.

The forwarded-deadline audit used the exact policy paths: `startup-logo.mjs`, `check-browser-world-scene.mjs` (`failureEpisode`), `frontend-checkpoint-notice-style.mjs`, `loading-recovery-style.mjs` and `original-pause-checkpoint-style.mjs`. The complete seven-episode entry audit found no other introduction skip: startup-logo and checkpoint-notice stay in the frontend; selector-recovery explicitly forbids gameplay launch; loading-recovery holds or fails loader responses. Only Options, HUD and pause-style enter a playable mission. Their existing 90000 ms episode caps, the 720000 ms series cap, resource ownership and cleanup rules are unchanged. Initial public popup/focus preparation is separate, but fresh native-state observation, passive witness installation, Space and atomic finalization all remain in the same at-most-2500 ms response, clipped to the already-running action and episode deadlines. This is a functional-contract migration, not a measured speedup or rendered acceptance.


## Proposed native-UI cumulative response contract v2

Generation 08 at exact candidate `f063de715a98936342ca51d7583750f10298ccc8` remains failed. Its HUD fallback introduction had a fulfilled second Space RPC but no second atomic after-state. The initial response began at 483.156 ms. A positively witnessed popup-owned, unchanged first response ended around 912.122 ms; retry popup-close/refocus preparation then consumed approximately 1692 ms. The finalizer expired within the old wall-clock response deadline. This does not establish failed input, World mutation or a performance speedup. Four episodes passed, HUD failed, and loading/pause were not reached.

The explicitly requested `public-setup-cumulative-response-v2` option changes accounting, not those historical results. It keeps one cumulative at-most-2500 ms active-response budget. Initial setup remains within the existing at-most-25000 ms action allowance. Only one retry is allowed, and only after the existing trusted, nonrepeated, prevented, popup-owned, same-World, unchanged-state predicate succeeds with actual atomic evidence. Only that retry's measured public popup-close/refocus preparation is excluded from active-response time. All fresh native reads, witness installation, real keyboard dispatch, atomic finalization and host work outside the measured preparation interval consume the original cumulative response budget. It does not restart a fresh 2500 ms budget.

The unchanged absolute action deadline, itself clipped to the already-running episode deadline, stays armed during preparation and always wins. Missing/stale/failed atomic finalization, unknown outcomes, actual keyboard errors, changed pause state and unproven ownership never authorize this exclusion or another key. No pending operation may dispatch late input after cancellation. Existing passive witness cleanup and primary-error handling remain unchanged.

The trace retains each response window, the one permitted preparation interval and its full phase trace, excluded duration, cumulative response duration, actual wall duration, both dispatch records and atomic outcomes when present. Successful infrastructure acceptance independently reconciles the intervals and deadlines. It also reconstructs retry authorization from the same atomic payload: matching nonempty observation/witness identities, a live witness, one trusted nonrepeat prevented popup-owned same-World record, unchanged typed native states and all three successfully settled witness/key/finalizer operations. A candidate outcome label alone, delivery failure, missing evidence or unexpected attempt count cannot authorize excluded time. Natural completion without a dispatch remains valid. Wall elapsed time must not be presented as the old single wall-clock response contract. The no-option default and all existing v1 callers remain unchanged; only native-UI ordinary Mission 1 entry and its pause-style supplement explicitly opt into v2. Seven episodes, 44 focus cases, 16 World comparisons, captures and all episode/series/resource caps are unchanged. This source proposal is not yet tested or rendered acceptance.
